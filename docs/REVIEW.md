# Project review (October 2026)

A full review of SwarmRide Bharat before and after the repository was made public. It covers:
- the **MATLAB code**, with MATLAB's Code Analyzer;
- the **C firmware**, with strict GCC warnings, GCC's static analyzer and the host test;
- the **simulation results**, with the 85-check verification suite;
- the **documents** and the **repository** itself.

An automated pull-request review by **CodeRabbit** uses the settings in [`.coderabbit.yaml`](../.coderabbit.yaml) once the CodeRabbit app is installed on the repository.

## 3. Firmware review

- **Match to the simulation:** each C function is a port of a named MATLAB function. The host test compares them on 2,700 random cases, including loads beyond the grid, full and empty banks, voltage saturation and every fault code. Worst LPV force error: 2 × 10⁻⁶ N in double, 0.03 N in float.
- **Fail-safe:** `sr_failsafe` can only *set* the latch. Nothing in the firmware clears it, so the contactor stays dropped until a manual reset. The contactor coil is also held by hardware (heartbeat, bank-OK, gate enable, E-stop), so the firmware can drop it but never hold it in.
- **Bounds:** the preview buffer is stored twice, so the window is always contiguous with no index arithmetic in the 100 Hz loop. Every array size is a compile-time constant from the generated header.
- **Float safety:** the generated tables are now written with an explicit cast (`SR_C(...)`), so the float build is warning-free under `-Wconversion`.
- **New:** `make strict` repeats this review build.

## 4. What this review does not cover

- **Physical validity of the vehicle parameters.** They are engineering estimates until RDSO data is available (see [VERIFICATION.md](../SwarmRide_Sim/VERIFICATION.md), section 4).
- **The hardware.** The bench prototype is designed but not built. Its tests are T1–T10 in [06_Test_Plan.md](../Bench_Prototype/06_Test_Plan.md).
- **Simulink models.** Code Analyzer checks `.m` files; the models are generated by the builder scripts it checked, and verified by the test suite.

## 5. Recommendations

1. **Patent: act now.** The repository is public, and a public disclosure can count as prior art against a later patent application. Talk to a patent attorney as soon as possible about filing, and about what the public date means for India and other countries.
2. **Install CodeRabbit** on the repository so every future pull request is reviewed automatically (settings already in `.coderabbit.yaml`).
3. **Keep the review build in the habit:** run `make strict` and `make test` in the firmware, and the Code Analyzer and `run_all_checks` in MATLAB, before every merge.
4. **Next engineering steps:** the state observer and CAN interface in the firmware; real vehicle data from RDSO; then the bench prototype build (Gate B).
